\begin{abstract}
Routing cost depends on table size, the working set that is queried, and whether routes capture parameters.
This paper asks which design choices in route matching matter, and when, and it reports the losses.
It measures the public RegexMatcher after its DFA construction, with the route target included.
The arms are a radix trie, a sequential scan, a static-path hash, and pinned routers in C, C++, Rust and Go.
Each external router runs in the best configuration its own documentation states.
The setting is one core of an \HostLCpu, with \RunCompiler, and every arm built for that processor.
v2 was not slower than the fastest competitor in \HOnePassed{} of \HOneCells{} cells, and faster in \HOneSuperior.
In those faster cells it took \HOneSupRatioMin{} to \HOneSupRatioMax{} of that competitor's time.
At the wild shape with \SizeTen{} routes, neither claim holds against gin.
v2 ran more instructions than gin in \HTwoLost{} cells.
It built large tables more slowly than the median competitor in \HFourLostBuild{} cells.
A minimal server answered more requests per second with v2 than with v1 in all \HSixCells{} cells.
That comparison is inside this paper's server and says nothing about the external routers.
End-to-end latency against those routers is absent from this manuscript.
A compile-time table passed its per-cell test in \HSevenHeld{} of \HSevenCells{} cells, so that hypothesis does not hold.
\end{abstract}

\begin{highlights}
\item Route cost depends on table size, working set and parameters.
\item Literal methods use a hash; other methods use a segment trie.
\item The matcher loses to gin on a small wild table.
\item Compile-time checks reject malformed routes at compilation.
\item End-to-end latency against external routers is unmeasured.
\end{highlights}

\section*{Supplementary material}

The following supporting information can be downloaded at
\PaperRepoURL: Table S1, every arm in every cell of
the main grid. Table S1 gives each value as the median over the arm's processes. It is the file
\texttt{results/round2/all\_arms.csv} of the paper's repository. Its columns are the arm's role, its processes and their statuses, and whether it takes part in the
cell, with the reason when it does not. They also hold the time per lookup, the raw and net
instructions, the branch misses, the cycles, and the L1d, L2 and DTLB misses. The allocations per
lookup, the build time, the bytes allocated by the build and the heap bytes of the table follow.
The latency percentiles and, for the Go arms, the cost of an empty call across cgo complete them.

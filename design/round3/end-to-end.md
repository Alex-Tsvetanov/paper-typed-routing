# Round 3: the end-to-end block

Status: DRAFT for review, written 2026-10-23. Not frozen. Nothing in it is measured. It freezes
only after its laptop hours are stated to Alex and he approves them. Later changes then go into a
revision log at its end.

Round 2 (`hypotheses-round2.md`, frozen) is the prior study. Its lookup grid (T0) is reused as
published. Round 3 asks whether the lookup results reach a client: each router hosted in an HTTP
server, load over loopback (T1), on both systems of one laptop.

## 1. What is compared, and what is not

The C and C++ routers run inside the paper's own server, one binary, the router chosen at start.
The Rust and Go routers run in separate programs, one per language, each in its language's
standard server (brief, section "Repository"). v2 also runs inside the Go and the Rust program,
behind its C interface (Alex, 2026-10-23). So these contrasts exist.

1. **Same server (tested).** In the C++ server, v2 against each C and C++ external router. The
   HTTP and I/O code is compiled once. The router sits behind one function pointer (round 2's
   `server/src/route.hpp`). A difference in req/s is a difference in routing, plus the router's
   effect on caches and branch predictors around it. In the Go and the Rust program, v2 behind its
   C interface against each of that program's routers: the language boundary counts against v2.
   Go calls it through cgo on Linux and through a DLL call (`syscall.SyscallN`) on Windows, so the
   Go boundary differs between the systems; Rust makes a plain C call on both. v2's code there is
   the C++ server's own build of it (one C-interface library, `server/capi/`, from the same CMake
   tree; `t3/build_programs.py` builds each program as one binary against it and records its path
   and sha256, and each program prints the library's `p2v2_build_info` at start). On Linux that
   library is compiled with `-fPIC` and the server's arms are not; the linker relaxes the calls in
   an executable, so the difference is expected to be negligible, and it is stated. Round 2's
   `ffi_call_ns` measured a call from C++ into Go, the other direction, so it is not this
   boundary's cost.
2. **Routing increment across servers (tested, Alex 2026-10-23).** Each program also has
   a null router, which answers route 0 without reading the path. The time a router adds per
   request is `1/X_router - 1/X_null` of its own program. v2's is the same difference in the C++
   server. The two increments come from different servers and runtimes (Go's scheduler and
   collector, tokio and hyper). Subtraction removes most of the server's own cost, not its
   interaction with the router. The paper states that boundary where it reports these numbers.
3. **Raw req/s across programs (reported only).** It measures server, runtime and language as
   much as routing. It is shown with the boundary stated and never tested.

Not done: Go and Rust routers inside the C++ server through round 2's FFI libraries. The brief
asks for separate programs, and a cgo call from a C thread is not Go's documented use.

## 2. Cells

- Shapes: mixed-disjoint and static (Alex, 2026-10-23). In round 2's grid all sixteen competitors
  take part in both at all five sizes (`results/round2/all_arms.csv`). Mixed-disjoint mixes
  literal and parameter routes; static is the case where a hash or a radix tree can lead. The
  choice is made before any end-to-end data exists. Round 2's lookup data are public and were
  read, so the choice is not blind to them.
- Sizes: m = 10, 100, 1,000, 10,000, 100,000.
- Systems: the laptop's Arch and its Windows. A C or C++ router that does not build on Windows
  is absent from its Windows cells, with the reason. Windows cells are counted on their own.
- A cell is one router, one size, one system.

## 3. Replicates

Round 2's sixteen seed pairs: table seeds 111 to 126 with ring seeds 211 to 226
(`hypotheses-round2.md`, section 4). One pair is one replicate. So every replicate has its own
table and its own ring, and the T0 to T1 carry-over is defined per pair. H6 of round 2 used one
pair only; that does not carry over to sixteen.

Per pair and size, one mirrored round per program: v2, each router in a fixed order,
null, then null, the routers in reverse order, v2. A fresh server per window, probed once, then
a 1 s warm-up and a 5 s window (H6's window, lab/t1). One arm's two windows are averaged.

With R = 16 pairs, the exact one-sided sign test reaches 2^-16 = 1.53e-5. The same-server family
of section 1, item 1 is at most 16 routers on Arch (9 C and C++, 4 Go, 3 Rust) and 15 on Windows
(r3 absent), x 5 sizes x 2 shapes: 310 cells. 0.025/310 = 8.06e-5, so D9 holds. The cross-server
family (section 1, item 2) is 7 routers x 5 x 2 x 2 = 140 cells, 0.025/140 = 1.79e-4.

## 4. Request sets

Generated by `t3/e2e_requests` from bench/core (round 2's generator, compiled unchanged), for
each pair and size:
- `routes.txt`: one route per line, `GET <pattern>`, rbench's syntax (`{p0}` a parameter,
  `{*p0}` a catch-all), in registration order. Route i is line i.
- `ring.txt` and `ring.expect`: the T0 ring of the pair (4,096 queries, all hits, uniform over
  the routes), in ring order, with each query's route and captured values. This is the measured
  request set. It holds the queried working set at 4,096 paths at every size, as T0 did.
- `all.txt` and `all.expect`: one target per route (h6_targets' rule), for the functional check
  of every route.

Mixed-disjoint tables are GET only (`TableSpec::methods` is 1 throughout round 2), so the routes
file of H6 needs no new form.

## 5. The contract of every server program

```
<program> --port P --workers 1 --routes FILE --router NAME [--check]
```

- Listens on 127.0.0.1:P. Ready when the socket accepts. One worker: one thread for the C++
  server, `GOMAXPROCS=1` for Go, a current-thread runtime for Rust.
- Routes: every router holds exactly the file's routes, route i being line i, so its table is
  round 2's T0 table. The program answers `GET /` and `HEAD /` itself, before any router, as
  route m with no captured value: the readiness probe of lab/t1. That is one comparison per
  request in every program and for every arm, the null arm included. (Round 2's adapters cannot
  express a route with no segment: Crow and Pistache refuse it, Oat++ crashed on it. A routes file
  that has `GET /` itself is routed normally.)
- Measured mode (no `--check`): a found route answers 200 with `Content-Type: text/plain` and
  the fixed 13-byte body `Hello, World!`. The handler folds the route id and, for every captured
  value, its length and first byte into a sink the compiler cannot drop. That is round 2's rule
  for every timed loop (`bench/core/runner.hpp`, header), so no router's capture work can be
  skipped by a lazy API.
- Check mode (`--check`): the body is the route id in decimal, then a tab and each captured value
  as the router returned it, then a newline. Same binary as the measured mode, one runtime flag.
- No route: 404, empty body. HTTP/1.1 keep-alive. A request body is not expected.
- Methods other than GET are never measured, and the programs answer them as their libraries do:
  the C++ server answers 405 when a GET route matches (round 2's harness rule) and HEAD through the
  GET route; the Rust program does the same; in the Go program net/http answers HEAD through GET,
  and httprouter, gin and chi answer by their own defaults.
- SIGTERM or SIGINT on Linux, Ctrl-Break on Windows (and Ctrl-C when the console delivers it; a
  child started in its own process group, as `t3/check_server.py` starts it, gets Ctrl-Break
  only): exit 0.
- Exit codes: 2 a bad command line or routes file, 3 the router refuses the routes, 1 any other
  failure.

## 6. Hosting, per language

- **C and C++** (`server/`, binary `mserver`): `--router v2|v1|null|crow|drogon|oatpp|pistache|
  boost-url|r3|uwebsockets|glaze|cpp-httplib`. The external arms are round 2's rbench adapters
  (`bench/arms/*.cpp`), compiled unchanged. A shim `core/runner.hpp` (`server/src/shim/`) turns
  `RB_ARM(Type)` into a registration with the server, so the code that lookups run is exactly the
  code T0 timed. Round 2's adapters take the path as `const std::string&`, so the server copies the
  request's path once into one reused string and hands that string to every arm, v2 and null
  included (`server/src/route.hpp`, `http1.cpp`). No arm pays a copy that another does not. The
  harness's 405 rule of round 2 is applied to arms without their own.
- **Go** (`server/go/`, binary `mserver-go`): `--router v2|httprouter|gin|nethttp|chi|null`. Go's
  `net/http` server, with each router as the `http.Handler` its library documents, so each request
  pays the library's own steps around the lookup: gin's `Engine` (`gin.New()` in release mode, the
  real v1.12.0 module, whose `tree.go` is the one round 2 vendored), chi's `Mux` (the real v5.5.0
  module; its lookup path is the same code as round 2's vendored v5.3.2), httprouter's `Router`,
  net/http's `ServeMux`. The lookup code is round 2's; T0 timed it without those steps.
- **Rust** (`server/rust/`, binary `mserver-rs`): `--router v2|matchit|path-tree|actix-router|null`.
  hyper's HTTP/1 server on tokio's current-thread runtime. Each router called as round 2's crate
  calls it (`bench/arms/rust/*.rs`).

Where the servers depart from round 2's single-threaded harness, and why:
- Go runs one goroutine per connection, and the scheduler can preempt one between a lookup and
  the read of its result even with `GOMAXPROCS=1`. So no Go arm shares lookup state between
  requests: each library's handler keeps its own per-request state (gin's and chi's pooled
  contexts, httprouter's params pool), and each route's handler closes over its id. The sink is
  added atomically, the same for every Go arm.
- net/http and the other Go libraries keep their own redirects (non-canonical paths, trailing
  slashes); no request set has such a path.
- httprouter and gin return a catch-all value with its leading `/`, chi and net/http without.
  Mixed-disjoint has no catch-all route, so the check never meets it. A shape with one would need
  round 2's declared semantics.
- hyper's 30 s header-read timeout is switched off, so no timer is armed per connection.
- Instruction sets, as round 2's (Appendix B): C and C++ `-march=native` (MSVC `/arch:AVX2`), Rust
  `-C target-cpu=native` (`server/rust/.cargo/config.toml`), Go `GOAMD64=v3`, the highest level
  the laptop runs (round 2: a `GOAMD64=v4` build refuses to start there), set by
  `t3/build_programs.py`. Each Go and Rust program prints its setting at start.

Arms per system, as built on the desktop on 2026-10-23:
- Linux (clang 22.1.8): v2, null, crow, drogon, oatpp, pistache, r3, uwebsockets, glaze,
  cpp-httplib. boost-url waits for Boost 1.92.0 headers in the image.
- Windows (MSVC 19.51): v2, null, crow, drogon, oatpp, uwebsockets, glaze, cpp-httplib. r3 includes
  POSIX headers. Pistache's CMake build passes GCC flags to cl; Alex chose its meson build with
  libevent there (not yet built). boost-url as on Linux.
- Go and Rust: all their routers on both systems (Rust on Linux waits for a toolchain in the
  image).

Pins: the latest release of each router (Alex, 2026-10-23), in a round-3 file of the server
(`server/cmake/pins-round3.cmake`) that overrides round 2's `bench/cmake/pins.cmake`, which stays
as round 2 measured it. Of the routers with a newer release, the re-check found the lookup code
unchanged (`router-survey.md`): cpp-httplib v0.63.0 (matchers), chi v5.5.0 (lookup), Drogon 1.9.14
(the transcribed file is the same blob), and Crow 1.3.5, a pre-release Alex chose on 2026-10-23
(its `Trie` is the same text). Go is 1.27.3 on both systems (Alex, the same day), installed outside
the package snapshot. RegexMatcher stays 2.1.0.0, the measured library. The servers' own
dependencies (hyper, tokio) are pinned by their own lock file.

## 7. Windows

- The C++ server gets an IOCP backend beside epoll. Both serve the same HTTP code and the same
  router interface.
- Go and Rust run natively on Windows.
- Compiler: clang-cl 22.1.8 on Windows (Alex, 2026-10-23), so the C++ server's compiler is the
  same on both systems; MSVC is the fallback for an arm that does not build with it. LLVM is not
  yet on the desktop or the laptop (Lab and Laptop requests), and `bench/cmake/isa.cmake` needs a
  clang-cl branch. The desktop's functional checks so far use MSVC.
- With MSVC every C and C++ target gets `/arch:AVX2` (`bench/cmake/isa.cmake`), the nearest MSVC
  has to Linux's `-march=native`, and `/Zc:__cplusplus /Zc:preprocessor /utf-8 /permissive-`
  (`server/CMakeLists.txt`).
- The IOCP backend (`server/src/loop_iocp.cpp`): one thread, AcceptEx kept posted, one overlapped
  receive per connection and at most one send in flight, completions that finish at once handled
  inline (`FILE_SKIP_COMPLETION_PORT_ON_SUCCESS`). The HTTP code is the epoll loop's
  (`answer_all`).

## 8. Load generator and runner

lab/t1's `t1gen` and `t1.py` are Linux only (epoll, `taskset`, `/proc`). Alex chose P2's own
portable generator and runner (2026-10-23), used on both systems with lab/t1's window rules, and
A/A-checked against `t1gen` on Linux before use (no arm compared).

**Generator `p2gen`** (`t3/gen/`, C++23; epoll on Linux, an I/O completion port per thread on
Windows). It does what `t1gen` does in its closed loop at depth 1 (`lab/t1/gen/t1gen.c`, header),
and no more:
- C keep-alive connections over T threads, each thread pinned to one CPU of `--cpus`; one request
  in flight per connection.
- Targets from a file, one per line; connection i of C starts at target i x N / C and walks the
  file cyclically, so every target is requested equally often.
- Framing that every program's answers pass: the status line, then a `Content-Length` header
  matched without regard to case (hyper writes it in lower case). In measured mode every answer
  must be 200 with the 13-byte body `Hello, World!`; anything else is counted as an error.
- A warm-up, then a measured window between two instants the main thread marks
  (`MEASURE_START`, `MEASURE_END` on stdout, as `t1gen`). Counted in the window only: completed
  answers, errors, timeouts (a connection with a request in flight and no progress for
  `--timeout-ms` is closed, counted, and reconnected), and the window's wall time. Latency per
  request from its send to the last byte of its answer, in a log-bucketed histogram, reported as
  percentiles.
- One JSON line at the end. No rate is computed inside it beyond completed answers over wall time.
- `--count N`: the desktop's functional mode. Exactly N requests over the connections, every
  answer checked, then counts only. It prints no time, rate or latency, so a desktop log never
  holds a number D7 forbids.

**Runner `t3/p2run.py`.** The frozen design only, not all of `t1.py`: per system, for each shape,
size and seed pair, one mirrored round per program; per window a fresh server pinned to the server
CPU, its start-up time recorded (readiness wait configurable, longer than lab/t1's 15 s, since
round 2's table builds alone reach 4.6 s at m = 100,000), one probe of `GET /`, then `p2gen` pinned
to the generator CPUs with a 1 s warm-up and a 5 s window. lab/t1's validity rules: the server
started and answered the probe; at least one completed answer; errors at most 0.1% of answers;
generator CPUs at most 90% busy; mean CPU clock within 2% of the session's. Plus the overload rule
of section 9. On Linux the samples come from `/proc`, as lab/t1's; on Windows from the per-CPU
counters and PDH's `% Processor Performance` that `lab/laptop/README.md` names, with affinity set
through `SetProcessAffinityMask`. One JSON line per window. H6's adaptive stop is not part of
round 3. `--count` mode on the desktop runs the same sequence with `p2gen --count`.

Both are measured first-party inputs, so they need their own D5 records (Laptop requests).

**D5 records and gate.** One record per host and sanitizer (`t3/sanitize.py`; L: ASan+UBSan, TSan,
MSan with round 2's instrumented libc++; W: clang-cl's ASan): the root project built under the
sanitizer (the server with every external arm, v2's C interface, p2gen, e2e_requests), its CTest
suite (with `test_p2v2`, v2's C interface on four cells, against the static library and, on
Windows, the DLL), the functional suite over every program built, p2gen in count mode against every
arm, and twelve request-set cells from the sanitized e2e_requests checked against the manifest.
The Go and Rust programs are built under the sanitizer where their toolchains allow (Go `-asan`
and `-race`, Rust `-Zsanitizer=address`); the rest are declared gaps in `t3/coverage.json`, not in
round 2's `bench/coverage.json`. What each target compiled is hashed as round 2 hashes it
(`lab/bin/inputs_hash.py`, project mode, RegexMatcher as a dependency root), and the Go and Rust
programs by their tracked files (`t3/source_hash.py`). The gate, `t3/check_records.py`, matches a
measured build's hashes with green records of the same host, compiler, configuration and pins, and
refuses any desktop run. The bring-up (`t3/jobs/bringup.py`) builds the measured programs, makes and
checks the request sets, and runs the suite and the runner in count mode first.

## 9. Known risks, from round 2's published laptop data

Mixed-disjoint at m = 100,000 (`results/round2/all_arms.csv`, `ns_median`, `build_s_median`):
- Four routers scan linearly. Lookup alone takes 30.1 ms (actix-router), 7.80 ms (Drogon),
  3.95 ms (Oat++) and 0.96 ms (cpp-httplib). On one server core that caps them near 33, 128, 253
  and 1,043 requests per second, before any HTTP cost. A 5 s window then completes few requests,
  and 64 connections queue behind each one. Rule (Alex, 2026-10-23): same windows; a router
  that cannot sustain the load is reported with its counts and leaves the tested family.
- Table builds take 4.6 s (Drogon) and 4.2 s (actix-router). A fresh server per window adds
  that start-up. The readiness wait must exceed it, and the time budget must count it.

## 11. Laptop time (estimate, to be replaced by a probe before the freeze)

Arms per round on Arch: C++ 11 (v2, null, 9 externals), Go 6 (v2, 4 routers, null), Rust 5 (v2,
3 routers, null): 22 arms, 2 windows each, 44 windows per pair and size. On Windows r3 is absent:

windows on Arch, 6,720 on Windows.

section 3.2). Arch 7,040 x 6.30 s = 44,352 s = 12.32 h. Windows 6,720 x 6.123 s = 41,147 s =
11.43 h. Together 23.75 h, 1.21 calendar days at plan v2's 19.68 measuring hours a day. Not counted, no measured basis yet: start-up at large m
(section 9), the A/A pilot, the H7 MSVC costs on the laptop (plan v2 uses the desktop's 0.33 h as
its estimate). A timing probe on the laptop replaces all of these before the freeze.

Measured by the probe (2026-10-25, one mirrored round of every arm at m = 10 and 100,000; pre-freeze,
never analysed): a window every 6.05 s at m = 10 and 6.56 s at m = 100,000 on Arch, 6.29 s and
